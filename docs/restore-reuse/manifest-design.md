# 地基设计：版本化 Manifest 与恢复校验

> 修订内容：清单改为放在数据旁边、校验失败立即取消、按清单下载。代码行号取自主线 `14c957e048b`。为什么要做地基见[总体方案](./overview.md)第 3 章；本文只写怎么做。

## 1. 目标

1. 备份时为每个 tablet 记录一份**完整性封闭**的文件清单：文件名、大小，以及可选的强摘要（SHA-256）；
2. 恢复时，每个 tablet 的下载阶段结束后，校验本地快照目录与清单**完全一致**：文件集合一致（不多也不少），每个文件大小一致。摘要校验由开关控制，默认关；
3. 校验不通过就明确失败，不会静默成功；
4. 旧备份、新旧版本互遇时，回到现有路径，行为和今天一样。

不在本文范围：R2 的逻辑摘要（L2）。它按"可见行"计算，和这里的文件摘要是两回事。

## 2. 现状

| 路径 | 备份时记录了什么 | 恢复时校验了什么 | 证据 |
| --- | --- | --- | --- |
| 远端仓库（S3 / HDFS / Broker） | 每个文件上传到 `<名字>.<md5>`；FE 核对上传的文件数和文件名，并把带 md5 后缀的文件名写进 jobInfo 的 `files` | 下载后校验 md5（始终开启）；**要下载哪些文件由远端目录列表决定，不和 jobInfo 的 `files` 比对** | `snapshot_loader.cpp:829-867`（上传）、`:931-1033`（下载）；`BackupJob.java:359-388`；`BackupJobInfo.java:640-644` |
| HTTP 快照（CCR 全量同步走这条） | jobInfo 的 `files` 只有文件名，没有大小，也没有摘要 | 要下载哪些文件由源 BE 的列表决定；默认只比较文件名和大小，下载后只校验大小；`enable_download_md5sum_check` 打开后才比较 md5 | `snapshot_loader.cpp:343`、`:576-599`、`:262-290`；`config.cpp:283` |
| 两条路径共同 | 备份元数据文件（meta、info）本身带 md5 后缀，下载时会校验 | — | `Repository.java:674-807` |

另外两点：
- HTTP 路径上，既有复用会把本地 rowset 文件**以远端文件名**硬链接进快照目录（`snapshot_loader.cpp:466-492`）。所以下载阶段结束时，本地快照目录里的文件名应该和源端一一对应，可以直接拿清单来比对。
- 远端仓库路径上传时会先把整个文件读一遍算 md5（`:838-840`），再读一遍上传。SHA-256 可以在算 md5 的同一遍读取里一起算出来，不增加 I/O。

## 3. 数据模型

**完整清单放在数据旁边，jobInfo 里每个 tablet 只存一个清单根摘要。** 根摘要在 jobInfo 里，而 jobInfo 本身有保护（远端仓库路径上带 md5 并在下载时校验；local 模式下由 FE 通过 RPC 直接下发），所以它是可信的；清单文件的摘要必须和根摘要一致才会被使用。

```text
BackupJobInfo（job 级新增）
  manifest_version   : int      // 1；缺失表示旧备份，没有 Manifest
  digest_algorithm   : string   // "sha256"；不算摘要时为 "none"

每个 tablet 新增
  manifest_root      : string   // 清单文件内容的 SHA-256（十六进制）

清单文件（每个 tablet 一个，JSON，按 name 排序）
  { "version": 1, "tablet_id": ..., "files": [ { "n": 文件名, "s": 大小, "m": md5?, "d": sha256? } ] }
  // m：远端仓库路径上远端对象名的 md5 后缀，用来直接定位对象；local 模式没有
  // d：摘要，按第 4 节决定有没有；.hdr 只记名字和大小
```

**清单文件放在哪**：必须放在 tablet 数据目录的上一层。旧版 BE 会把 tablet 目录里的文件全部下载下来，再随快照挪进 tablet 数据目录，它不认识的文件会带来不可控的风险。放在上一层，旧版 BE 看不到它。

```text
远端仓库：…/__ss_<label>/__ss_content/__db_<id>/__tbl_<id>/__part_<id>/__idx_<id>/
            ├── __<tablet_id>/                    ← 数据文件，不变
            └── __manifest__<tablet_id>.<md5>     ← 新增，随上传一起写

local 模式（CCR）：上游 BE <storage_root>/snapshot/<时间>.<序号>.<超时>/<tablet_id>/
            ├── <schema_hash>/                    ← 数据文件，不变
            └── manifest                          ← 新增，做快照时写
```

- local 模式下，下游 BE 通过已有的 `/api/_tablet/_download` 按固定路径拉取清单。这个接口允许下载 BE 存储根目录下的任何文件（`download_action.cpp:195`），不需要改动；
- 体积：jobInfo 每个 tablet 只多约 80 字节，10 万个 tablet 约 8 MB。清单文件每个约 2～4 KB，和数据放在一起。
- 为什么不放进 jobInfo：实测放进去以后，每个 tablet 多 4.4 KB，10 万个 tablet 多 425 MB，jobInfo 变成原来的 2.7 倍；而 RestoreJob 每次状态变化都会把 jobInfo 整个写进编辑日志。local 模式下还会更快碰到 `getSnapshot` 的 2 GB 上限（`FrontendServiceImpl.java:4209`）。
- ccr-syncer 把 jobInfo 当通用的 map 解析再写回（`ccr-syncer/pkg/ccr/job.go:541`），所以不认识的字段会原样保留。根摘要用字符串存，不会有大整数精度问题。

## 4. 生成（备份侧）

| 路径 | 谁写清单文件、何时写 | 摘要 |
| --- | --- | --- |
| 远端仓库 | BE 把这个 tablet 的数据文件全部上传后，生成清单并上传，然后把根摘要报给 FE（`TFinishTaskRequest` 新增按 tablet 的 `manifest_roots`） | **默认就算**：在算 md5 的同一遍读取里一起算 SHA-256，基本不增加 I/O |
| local 模式 | BE 做完快照时，把清单写进快照目录，然后把根摘要报给 FE | 默认**不算**（源端没有上传环节，算的话整个快照要多读一遍）；备份属性 `manifest_digest = "true"` 时才算 |

FE 在汇总时把根摘要写进 jobInfo。只要有一个 tablet 没有报根摘要（例如 BE 是旧版本），整个 job 就不写 Manifest（`manifest_version` 缺失），退回旧备份的行为，不写半份清单。

## 5. 校验（恢复侧）

1. FE 构造 DownloadTask 时，把每个 tablet 的根摘要带给 BE（`TDownloadReq` 与 `TRemoteTabletSnapshot` 各新增一个可选字段）；
2. BE 先取清单文件，算它的 SHA-256 与根摘要比对，不一致就判失败；
3. **按清单下载**：只下载清单里的文件。远端仓库路径用清单里的 md5 直接定位 `<名字>.<md5>` 对象，不再依赖目录列表；远端目录里多出来的文件（例如上传重试留下的孤儿文件）一律忽略。local 模式下，按血缘硬链接复用的逻辑不变，其余文件按清单下载；
4. 下载（含硬链接）完成后，列出本地快照目录，逐项核对：
   - **集合**：文件名集合与清单完全相同；
   - **大小**：每个文件大小都相等，硬链接复用的文件也要核对；
   - **摘要**（开关打开且清单里有摘要时）：计算 SHA-256 并比较；
5. 核对失败时，BE 先对这个 tablet 重下一次，重试时关闭硬链接复用、清空目录、全量下载；仍然失败，就返回专门的错误码，带上第一个不一致的文件名、期望值和实际值；
6. **FE 收到这个错误码就立即取消恢复任务**，状态里写明原因，不再等到超时（恢复任务默认超时 1 天，CCR 场景下 syncer 会一直卡着）。其他下载失败保持现有行为；
7. BE 在完成报告里带回通过校验的副本（`manifest_verified_tablets`，按副本计数），FE 汇总后展示。

## 6. 兼容

| 情况 | 行为 |
| --- | --- |
| 旧备份（没有 Manifest） | 走现有路径；`SHOW RESTORE` 显示没有 Manifest |
| 新 FE + 旧 BE（备份） | 没有根摘要上报，整个 job 不写 Manifest |
| 新 FE + 旧 BE（恢复） | 旧 BE 忽略根摘要，按现有方式下载，也不回报校验结果。FE 把这些副本记为"未校验"，不判失败 |
| 旧 FE + 新 BE | 请求里没有清单，BE 不做校验 |
| 新备份被旧 FE 恢复 | 旧 FE 忽略新字段，按现有路径恢复；清单文件在 tablet 目录的上一层，不会被下载 |

## 7. 开关与展示

- BE 配置 `restore_manifest_check`，默认 `true`：做集合和大小校验。关掉后行为和今天一样；
- BE 配置 `restore_manifest_digest_check`，默认 `false`：摘要校验；
- 备份属性 `manifest_digest`：HTTP 路径是否计算摘要，默认 `false`。远端仓库路径总是计算；
- `SHOW RESTORE` 完整输出的末尾（`ReuseEstimate` 之后）新增一列 `ManifestCheck`，JSON 格式：`{"version":1,"algo":"sha256","verified_tablets":N,"unverified_tablets":M,"digest_checked":bool}`，没有 Manifest 时显示 `\N`。

## 9. 已定

1. **校验失败**（2026-09-28 定，09-29 补充）：先重下这个 tablet 一次，重试时关闭硬链接复用、全量下载；仍然失败，就返回专门的错误码，FE 立即取消恢复任务，不等超时。
2. **HTTP 路径的摘要**（09-28）：默认不算，备份属性 `manifest_digest = "true"` 时才算。
3. **新 FE + 旧 BE 恢复**（09-28）：记为"未校验"，在 `SHOW RESTORE` 里展示，不判失败。
4. **清单放在哪**（09-29）：完整清单放在数据旁边、tablet 目录的上一层；jobInfo 只存每个 tablet 的根摘要。
5. **下载依据**（09-29）：有清单时按清单下载，远端目录里多出的文件忽略。
6. **远端清单对象名**（09-30）：后缀用根摘要的前 32 位十六进制，不用清单内容的 md5。这样 BE 只凭 jobInfo 就能拼出对象名，不用列 `__idx_` 目录（S3 的列举是递归的）；32 位长度和现有的"文件名.md5"格式一致。
7. **清单取不到**（09-30）：第一版维持现状，按普通下载失败处理，等到超时。清单不存在基本意味着仓库损坏或快照已过期，这种情况下数据文件同样下不来，行为一致。以后 CCR 场景真的被卡住，再改成"重试几次仍不存在就立即取消"。
8. **本地多余文件**（09-30）：远端仓库路径按清单下载时，本地快照目录里不在清单里的文件全部删除（包括 `LOADED` 标记和扩展名不认识的文件）。这发生在文件挪进 tablet 数据目录之前。
9. **local 模式多一次请求**（09-30）：每个 tablet 多一次取清单的 HTTP 请求，可以接受。以后可以改用清单里的大小，省掉逐个文件的 HEAD 请求。
