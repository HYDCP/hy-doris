# Doris Restore 下载优化总体方案

> 本文只写当前结论，实测证据见内部实测记录。
> **注意：本文的"状态"和路线写于开发早期，部分已过时（地基、R2 首版、增强项、原子恢复路径均已实现）。最新状态以 [README](./README.md) 为准。**
> 状态：**谱系戳与影子统计**已实现并在测试集群上验证完；**地基**可开发、未开发；**R2 首版已实现**（测试环境下，灾备来回切换演练省下载 63%，错误复用 0）；**R0** 只做观测（多副本下既有复用生效）；**门 1 未关**，已改为价值核对、不再阻塞开发。
> 代码行号取自 Doris 主线 `14c957e048b`。

# 1. 目标与原则

Restore 会把备份中的数据文件全部下载到目标端。目标端往往已经有大量相同或逻辑相同的数据，这些下载是重复的；在灾备、跨机房、大表重建场景下，下载量直接决定 RTO。

- **只在证明成立时复用**，证明不足一律退回完整下载，最坏情况与现有 Restore 一致；
- **正确性优先于命中率**：文件名、Rowset ID、版本号、文件大小都不能单独作为复用依据；
- 不承诺固定复用率、固定 RTO 或"所有冷数据零下载"。

**不存在免费的方案。** 目标端数据一旦被 Compaction 改写、旧文件又被 GC 清掉，要继续避免下载，就必须额外保留某种东西：旧文件本身、可重放的增量日志，或足以证明本地状态的逻辑身份。本线只走最后一条，即 R2；什么都不额外保留、只利用碰巧还在的字节，就是 R0。

# 2. 架构

三部分，**不是升级关系，也不互为前置**：

| | 做什么 | 当前状态 |
| --- | --- | --- |
| **地基** | 版本化 Manifest + 强摘要（记录，校验默认关） | 按数据完整性独立立项；可开发、未开发（第 3 章） |
| **R0** 物理文件复用 | 本地文件与备份文件逐字节相同时 hard link，不下载 | Doris 3.1.4 已自带基于血缘的同类能力；单副本测试环境判定增量价值≈0，目标环境存疑（第 4 章） |
| **R2** 分区级逻辑等价复用 | 证明本地分区与备份快照的查询可见数据一致，整分区保留 | 覆盖被改写数据的唯一路径；首版已实现（第 5 章） |

| | R0 | R2 |
| --- | --- | --- |
| 命中前提 | 文件逐字节相同 | 分区版本未前进且同源 |
| 复用粒度 | 文件级，可部分复用 | 分区级，全有或全无 |
| 额外代价 | 摘要比对 | 一次全分区归并扫描 |
| 失败去向 | 逐文件下载 | 整分区下载 |

## 2.1 复用决策链

各部分都落地后，Restore 的复用决策是一条链：

~~~text
读取远端 Manifest                       ← 地基
  ↓
① 分区级：L0 谱系 + 版本锚点通过？      ← R2
    ├─ 通过 → 按档位做 L1/L2 → 一致则整分区保留，跳过其全部文件
    └─ 不通过 ↓
② 文件级：本地有逐字节相同的候选？      ← R0 / 既有血缘复用
    ├─ 有 → 同盘 hard link
    └─ 无 ↓
③ 从远端仓库下载                        ← 兜底
~~~

分区级必须在前：可以整体跳过大量文件，避免为已确定保留的分区逐文件建计划。

## 2.2 正确性不变量

所有复用路径都必须遵守，不得以提高命中率为由放宽：

| | 内容 | 对 R2 的含义 |
| --- | --- | --- |
| I1 | 只有证明明确成立的对象才能跳过下载 | L0 通过不等于免校验 |
| I2 | 最终 staging 文件集合必须与远端 Manifest 一致 | R2 保留分区时该分区不进入集合比对，须单独定义等价条件 |
| I3 | 从证明到物化之间必须受保护或重新验证 | R2 需发布前持锁复查版本 |
| I4 | 复用只发生在 staging，不修改在线 Tablet | **R2 首版走非原子路径保留在线分区，是本条的例外** |
| I5 | 物化失败或候选消失必须下载，不能忽略 | 一致 |
| I6 | 开关只影响下载量和耗时，不改变最终数据、版本和 TabletMeta | 一致，回归测试的核心断言 |
| I7 | 所有暂存 Tablet 完成前不得替换正式表 | 一致 |
| I8 | 取消、失败、replay 后不留可见的半成品 | 一致 |

I4 是唯一需要为 R2 破例的一条，因为 R2 保留的是在线分区本身。立项时须单独论证，并给出补偿措施（发布前持锁复查版本）。

## 2.3 工程约束

- **同盘 placement**：hard link 只在同一文件系统内有效，跨盘回退下载。这是部署约束，须在规划期显式判定。
- **开关与降级**：默认关闭 → 影子规划 → 灰度；Capability 协商，新旧版本互遇一律回到现有下载路径；摘要不一致属正常降级，不告警为失败。
- **指标口径**：`eligible / reused / downloaded bytes` 在各路径间可加总、可对比；R2 的分区保留要能折算成等价 bytes。高基数的文件名不作长期 Metrics 标签。
- **原子性表述**：只有单表可见性原子，不得描述为"多表同时原子切换"。发布钩子、长查询排空、旧表找回属于调用方的恢复编排能力，本线不提供。

# 3. 地基：版本化 Manifest 与强摘要

按数据完整性立项，**不与任何复用能力的 ROI 绑定**：即使复用路线整体不推进，本章也应交付。

## 3.1 缺口

- `snapshot_loader.cpp:343`：HTTP Snapshot 的文件清单只是换行分隔的文件名，不是版本化、完整性封闭的 Manifest；
- `config.cpp:283`：HTTP 下载的 MD5 校验默认关闭。此时跳过下载的判定就是"文件名 + 大小"，下载后也只校验大小；增量同步的 `ingest_binlog` 受同一开关控制；
- 远端仓库（S3 / HDFS / Broker）路径：每个文件的 MD5 写在远端文件名里，上传与下载两端都校验，且始终开启；
- 两条路径都**不核对文件集合**：恢复时只看远端目录列表或 HTTP 文件清单，不与 jobInfo 里的逐文件清单比对；
- 既有的血缘复用（第 4 章）完全依赖 `source_rowset_id` 正确，没有任何内容校验兜底。

即：**当前 Doris Restore 的 HTTP 快照路径（CCR 全量同步走这条）在默认配置下不校验下载内容。**地基首版的内容校验只需覆盖 HTTP 快照路径；文件集合校验两条路径都要做，可直接用 jobInfo 里现成的逐文件清单。

## 3.2 交付

1. **版本化 Snapshot Manifest**：完整列出恢复所需对象、大小、强摘要（推荐 SHA-256，显式记录 `digest_algorithm`）、算法版本与元数据引用，对快照文件集合完整性封闭；
2. **校验默认值**：文件集合完整性与大小校验默认开（成本约为零）；摘要记录在 Manifest 中，摘要校验默认关、按需开启，理由见 3.3；
3. **旧备份兼容策略**：没有强摘要的历史备份如何处理（拒绝复用，或允许下载后按旧 MD5 校验），须在设计中定死；
4. **Manifest Root**：可快速校验清单整体，但逐文件条目仍是权威；它不证明不同物理布局的逻辑等价。

跨版本兼容与旧备份策略待单独评估。

## 3.3 为什么摘要校验默认关

1. **上游有意做了同样的取舍。** `enable_download_md5sum_check` 默认关（测试环境实测确认目标版本仍是 `false`），`enable_compaction_checksum` 同样默认关。Doris 的立场是复用必须免费：凡是要全量读一遍数据才能证明的事，都不默认开。既有的血缘复用只比元数据、不读文件，正是这条立场的产物。
2. **摘要成本不对称，贵在最需要它的地方**（见下表）：开销恰好落在要跳过下载的那些文件上。
3. **该开销从未实测。**

| 路径 | 摘要成本 |
| --- | --- |
| 下载的文件 | 约等于免费：字节本来就在内存里过一遍，流式哈希，不额外读盘 |
| 复用的文件（跳过下载的） | 一次全量本地读，纯新增 I/O |

Manifest 里的强摘要仍然交付，它是按需校验、事故排查与将来任何复用证明的依据；只是不默认校验。

**这道算术题与 R2 的 L2 是同一道**：都是"为跳过下载付一次全量本地读"，由同一个比值决定——本地读带宽对有效恢复带宽。要重新开启默认校验，或者定 L2 的默认档位，都要先拿到两个带宽数：

| 数 | 谁用 | 怎么取 |
| --- | --- | --- |
| 归并扫描带宽 | R2 的 L2 | 全量扫描一个冷分区并计时（5.5） |
| 裸顺序读带宽 | 地基的摘要 | 对一个大 segment 文件计时做一次哈希，比归并扫描快，是上界；需要 BE shell |

# 4. R0：物理文件复用

## 4.1 现状：Doris 3.1.4 已有基于血缘的本地复用

`SnapshotHttpDownloader::_link_same_rowset_files()`（`be/src/runtime/snapshot_loader.cpp`）比较本地与远端的 tablet meta，能对上的 rowset 直接 hard link、不下载。匹配键是 `RowsetMetaPB.source_rowset_id`，并要求版本区间相同。

- **粒度是 rowset 级，不是 tablet 级。** Compaction 输出的是全新 rowset，不带 `source_rowset_id`，一轮 Compaction 血缘就断——失效边界恰好是 R2 的目标域。
- 单副本测试环境：血缘完好时，552 MB 与 1 KB 的恢复耗时相同（6 s）；任一侧 compaction 后升到 15 s。
- `source_rowset_id` 在全量重建与增量同步落地时都会写，正常导入不写（3.1.4 实测）。

证据见内部实测记录。

## 4.2 门 3：R0 的增量价值

R0 原设计（显式 Proof / Plan / Executor + hard link + 逐文件回退下载）要复用的"逐字节相同的文件"，和既有血缘复用覆盖的是同一部分数据；没有血缘时，独立写出的两份文件可以有 97% 字节不同（门 0：同一 tablet 的两个副本），"字节相同但没有血缘"只是极窄的角落。**故 R0 不作为独立阶段立项，降级为"既有血缘链路的加固与观测"。**

**这个结论只在单副本测试环境验证过。** 其他部署上有两处可能不同，结论是否适用待查：

1. **增量同步写入的下游 rowset 可能没有 `source_rowset_id`**，而 3.1.4 会写。原因未查，最可能是版本不同；
2. **上下游可能都是三副本。** 在 3 副本测试集群上验证过：备份固定选同一个上游副本，下游 3 个副本都从它恢复，全量同步之间血缘保持，3 个副本全部命中；**多副本本身不会使复用失效**。唯一稳定的损失在增量同步：syncer 把下游副本配给不同的上游副本拉 binlog，每个 tablet 有 2 个副本的增量部分要重新下载。

若既有复用在目标环境实际不生效，"R0 增量价值≈0"就不成立：R0，或者升级到增量同步会写来源的版本（只对升级后同步的数据有效），可能重新有价值。

## 4.3 降级后的范围

D1 已关（09-28）：多副本下既有复用生效，R0 降级版**只做观测，不做修复**。

- 由 BE 按"下游副本 × tablet"直接上报每次下载任务的硬链接数、下载文件数与字节数（取代统计日志条数）；
- 把既有复用纳入统一的 `eligible / reused / downloaded bytes` 口径；
- 血缘失效的可观测化：目前失效是静默的，DBA 看不出这次 Restore 为什么突然变慢。

- 增量同步那 2/3 副本的损失在 syncer 侧修，不改 Doris：让下游各副本都从备份会选中的上游副本拉 binlog，或者评估 `feature_single_replica_ingest_binlog`（它写入的 `source_rowset_id` 指向哪里待核实）。

**与 R2 的关系：两者覆盖的是不同的情况，互为补充。** 既有复用覆盖"物理 rowset 没变"的情况，包括增量同步后和原子恢复；R2 覆盖"物理上变了、逻辑上没变"的情况，包括 compaction、上游换副本、Clone，以及没有既有复用的远端仓库路径。所以影子统计 `ReuseEstimate` 只是 R2 的判定结果，不是实际下载量：增量同步后的全量它记为不可复用，实际上既有复用省下了 99% 以上；compaction 后它记为可复用，实际上还是下载了。**判门 1 时，R2 的增量价值要扣掉既有复用已经省下的部分**，需要上面 BE 侧的观测数据。

R0 原完整设计已归档，其正确性不变量已并入 2.2。

# 5. R2：分区级逻辑等价复用

完整论证见 [R2 详细设计](./r2-detailed-design.md)。

## 5.1 命题

证明**目标端现有分区的查询可见数据 == 备份快照的查询可见数据**，从而保留该分区、不再下载。不要求内部状态一致：rowset_id、文件字节、delete bitmap 的内部表示跨集群本就不可比。

## 5.2 判定分层

| 层 | 内容 | 成本 | 性质 |
| --- | --- | --- | --- |
| L0 | 谱系戳 + 版本锚点 | 零 | 必要，不充分 |
| L1 | Schema 签名、tablet 数、逻辑行数 | 极低 | 快速否证 |
| L2 | 顺序无关的分块强摘要全等 | 一次扫描 | 充分（摘要强度意义下） |

L2 做成可配置档位 `off / sample / full`，**默认值按分区来源区分**：Restore 建的分区（版本一次性赋值，构造性成立）可支持 off；增量建的分区（版本相等是靠行为维持的不变量，没有检查点）建议从 sample 起步；**Unique 表不允许 off**（见 5.4）。

## 5.3 必须新增的两样东西

1. **分区级谱系戳**：`Partition` 新增一个 gson 字段，在 `RestoreJob.allTabletCommitted` 对本 job 的全部分区统一写入，数据源是 `BackupJobInfo`；覆盖已有分区、新建分区、新建表、原子恢复四条路径（只写在版本回写处只覆盖第一条，CCR 全量同步常走的后两条会漏掉）。**透传陷阱**：新建路径上的分区对象本身就是上游对象的深拷贝，上游的旧戳会原样带过来，所以先清后写：BackupMeta 加载后清空，提交时用本 job 的 jobInfo 写入。已实现。谱系戳有前置期：不埋就没有历史数据，R2 立项时只有埋点之后恢复的分区可用。
2. **顺序无关的逻辑摘要**：规范化行编码 + 逐行强哈希后按大整数求和（multiset hash，不用 XOR）+ 内容定义分块。现有的 32 位 tablet checksum 顺序相关，不能用。

## 5.4 首版边界

- 走**非原子恢复路径**：分区已存在且 range 一致时（A1 分支），现有 Restore 本来就复用本地 tablet，在这里加判定即可。原子换表路径下保留本地分区涉及 tablet 归属、RestoreFileMapping、editlog 与换名失败窗口，放到二期；
- 要求两端**版本相等**；
- 满足**四个启用条件**才进入校验：L0 通过、分区足够大、足够冷、数据在本地。冷度只作成本闸，不作一致性证据；
- 一切不确定都降级下载。

**Key 模型**（目标场景中的表以 Unique Key 为主）：

| 模型 | 是否可证 | 说明 |
| --- | --- | --- |
| Duplicate | ✅ | 存储多重集即可见多重集，扫描后直接求摘要 |
| **Unique** | ✅ 须按"可见行"求摘要 | REPLACE 语义下，每个 Key 的胜出行由版本序（或 sequence 列）唯一确定，与聚合顺序无关 |
| Aggregate | ❌ 永久不支持 | float/double 的 SUM/AVG 不满足结合律，逻辑等价不可证 |

- **MoW**（`enable_unique_key_merge_on_write`，新建表默认 `true`）：可见行 = 存储行 − delete bitmap 标记的行。bitmap 按 `(rowset_id, segment_id, version)` 存在 tablet meta 里，两端 `rowset_id` 不同，没法直接比对，只能带 bitmap 扫描、比对作用效果。
- **MoR**：可见行由读时按版本序归并 REPLACE 决定。

**首版必须纳入 Unique，否则覆盖率约等于 0。** 成本模型不变（本来就是一次全分区归并扫描），变的是必须实现 Unique 的规范化路径。

**Unique 放大了版本对齐失效的后果**：在 Duplicate 表上，版本偏移表现为行数多了或少了，L1 就能否证；在 Unique 表上，版本偏移表现为某些 Key 选错了胜出行，行数完全相同，只有 L2 能发现。这就是 Unique 表不允许 `off` 档的原因。

## 5.5 性能判据

主导成本是一次全分区归并扫描。1 TB 本地 SSD 约 10～30 分钟；对比下载 1 TB：1 Gbps 约 2.4 小时、10 Gbps 约 15 分钟。**有效恢复带宽低于本地扫描带宽时就划算**，跨机房场景几乎总是成立，但必须实测。

三项摊销：备份侧按 `(tablet, version)` 缓存摘要（冷分区版本不变，稳态下成本趋近于零）；目标侧只对 L0 通过的分区计算；冷却到远端的数据排除在外（扫描≈下载）。

## 5.6 对调用方的外部要求

以下三件事在本线之外。调用方不提供时，R2 在相应场景下不产生收益：

1. **表级来源描述符**：由跨集群复制工具在建立复制关系时写入，用于识别增量同步期间新建分区的谱系。本线不实现。
2. **换源时改写来源描述符**：复制来源变更后，描述符若仍指向旧源，谱系匹配全部失败——方向安全，但恰好在切换后最想省下载的时刻整体失效。
3. **版本对齐校验**：增量同步的上下游版本相等是靠行为维持的不变量，目前没有任何一环检查它。任何依赖"版本相等"的判定，都应要求调用方提供这项校验。

# 6. 已确认的事实

## 6.1 实测

| 事实 | 证据 |
| --- | --- |
| 逻辑相同的数据可以字节完全不同：同一 tablet 两个副本、同版本同行数，97.35% 字节不同，差异从第 0 字节起均匀分布。字节级确定化不成立，被改写的数据只有 R2 能覆盖 | 内部实测记录 |
| 两端跑同一套 compaction 策略时，会合并出相同的版本边界，差的只是字节（SAMEROW 高、COMPACT≈0） | 内部实测记录 |
| 单侧一次 compaction 就能把 EXACT 从 100% 打到 0 | 内部实测记录 |
| Doris 3.1.4 的 Restore 自带基于 rowset 级血缘的本地复用 | 内部实测记录 |
| 3.1.4 在全量重建与增量同步落地时都会写 `source_rowset_id` | 内部实测记录 |
| 多副本下，同一 rowset 的各副本字节可以不同 | 内部实测记录 |
| 增量同步写入的下游 rowset 可能没有 `source_rowset_id`（与版本有关） | 内部实测记录 |
| 目标场景中的表以 Unique Key 为主 | 定性结论，没有逐表占比 |

# 7. 决策门

| 门 | 问题 | 结论 |
| --- | --- | --- |
| 门 0 | Compaction 输出能否确定化 | ✅ 不能。被改写的数据只有 R2 能覆盖 |
| **门 1** | 长历史表的真实复用率 | 🟡 **未关**；2026-09-28 起不再阻塞开发，改为价值核对（R2 纳入完整版本先做） |
| 门 2 | 目标表的 Key 模型能否证明逻辑等价 | ✅ 以 Unique 为主，可证（须按可见行求摘要）；R2 首版须支持 Unique |
| 门 3 | R0 的增量价值 | ✅ 约等于 0（单副本测试环境；3 副本测试集群复核，同样成立）；⚠️ 增量同步写入的 rowset 缺 `source_rowset_id` 的原因待查，见 4.2 |

## 7.1 门 1 怎么判

探针把每个源端 rowset 归为 EXACT / SAMEROW / COMPACT / DIFFROW / MISSING（定义见内部探针说明）：

| 实测形态 | 含义 | 决策 |
| --- | --- | --- |
| EXACT 高 | 既有血缘复用已覆盖（前提是它在目标环境生效，见 4.2） | 不需新做 |
| SAMEROW + COMPACT 高 | 只有逻辑等价能覆盖 | R2 值得做 |
| MISSING 高、前两者都低 | 数据本来就得下载 | 只交付地基，不做复用 |

读数须知：

- **EXACT 是元数据判定**：版本区间、行数、大小、段数相等即判定，从不比内容，只能读作上界，也不再校准。它虚高的部分实际属于 SAMEROW。
- **多副本环境以探针的"多副本复核"段为准。** 主表按首副本对首副本统计，在多副本下不可信。
- **现有读数都不能关门**：测试环境三轮来自同一张 3 天窗口的表，方差过大；另一次首测只有 4 个分区，而且是在探针能比较全部副本之前测的。
- "分区越老 EXACT 越低，长历史表 R0 约 10～15%、R2 约 85～90%"只是基于 3 天窗口的外推，至今未验证。常态是"近期分区只写入一次 + 多副本"，**门 1 的测法须重定**。

## 7.2 关门 1 还缺什么

- 一张有数月历史的真实业务表，用新版探针复测；
- 同一趟取两个带宽数（3.3）；
- 门 2 的遗留摸底：MoW / MoR 占比、`sequence_col`、Aggregate 表占比；
- 弄清既有复用在目标环境是否生效（4.2）——它决定 EXACT 那部分是不是真的"已经免费"。

除了人工测量，还有一条途径：谱系戳上线后，从影子统计里直接读"若启用 R2 可跳过多少"。

# 9. 风险与明确不做

| 风险 | 控制 |
| --- | --- |
| 用弱证明换命中率 | 证明不足一律降级下载 |
| 把命中率当作正确性前提 | L0 不通过是正常事件，不得触发失败 |
| 地基被复用 ROI 连带砍掉 | 地基按数据完整性独立立项 |
| 埋点滞后，R2 立项时没有历史数据可用 | 谱系戳随地基先做、不等门 1；但要上线运行后才开始积累历史 |
| 基于不足的样本改排期 | 门 1 须用长历史表复测，单表短窗口不作依据 |
| ccr-syncer 默认用原子恢复做全量同步，而 R2 首版只覆盖非原子路径：按默认配置，R2 首版对 CCR 全量同步的覆盖约为 0（测试集群实测：原子模式下全部计入 `l0_passed_but_atomic_restore`）。既有的物理复用在原子恢复下仍然生效，所以受影响的只是"物理变了、逻辑没变"那部分 | 后续已实现原子恢复路径（见 README）；也可评估改为非原子全量同步的代价 |

明确不做：

- 不为提高命中率改动 Compaction 或 flush 的输出，也不给 Compaction 增加血缘或证书传播——血缘只能加速候选查找，永不作证明；
- 不建立全局历史证书（HistoryRoot），不让 Compaction 理解复制历史；
- 不提供数据库级的全局原子切换；
- 不承担业务校验审批、长查询排空、多表联查协调或外部系统的进度提交；
- Cloud / 存算分离模式的本地复用不在本线范围。
